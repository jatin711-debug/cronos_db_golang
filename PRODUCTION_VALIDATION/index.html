    Deployment validation and remaining release gates¶

    Local single-host campaign — 2026-11-11¶

    The gates at the end of this record need separate hosts. To find software defects before that, the acceptance suite gained a soak (TestSoak), a growth test (TestClusterGrowsFromThreeToFive) and a CDC failover test, run on one Windows machine with the nodes as processes: three nodes of 384 MiB and 2 CPUs each, encrypted WAL, every_event fsync, RF=3/minISR=2, replication TLS, a CDC webhook, a slow consumer group and a dead-lettering topic, at 100 publishes per second with bursts of 500.

    It found three defects in v0.12.0, fixed in v0.12.1: a leader that came back with an empty disk had its followers delete their logs; CDC skipped events after a failover once anything had been dead-lettered; and every replicated append read the log back from disk, which held the cluster to about 50 publishes per second. With the fixes, a 25-minute soak passed all seven of its disruptions (leader lost, leader frozen, leader lost during catch-up, CDC destination down, consumer group behind, a leader replaced by an empty node, whole cluster lost) and ended with every acknowledged event delivered to both consumer groups and exported. The growth test (three to five nodes, a leader lost during the handoff, rolling restarts, an empty replacement, a removal) and the rolling upgrade drill from v0.12.0 also passed. The v0.12.1 notes give the figures.

    This does not close the gates below. The soak ran for 25 minutes on one host, not 24 to 72 hours on separate ones; growth, drain and replacement ran as processes, not on separate hosts or Kubernetes; power loss was not tested; and the latencies are those of a shared desktop machine. A 24-hour run of TestSoak on one machine is the next step, before the separate-host run.

    v0.13.0 — 2026-11-13¶

    Two growths found after v0.12.2 are stopped, and the take-up guard's firing on ordinary restarts (see v0.12.2 below) is removed at its cause.

    Consumer progress. A group's completion floor stopped at the first entry it does not take: another topic's event in the same partition, or the term-start record each new leader writes. So after the first failover every group kept its progress as per-event records until the entry left the log. The redelivery sweep now raises the floor over such entries and the group's completed events. An in-process test with two topics interleaved on one partition ends with the group's floor at the end of the log and no records left; without the change the floor stays at offset 0 with 10 records above it.

    Metadata log. Raft's default snapshot threshold (8,192 entries) meant the metadata log was never snapshotted and every start replayed all of it. It is now snapshotted every 128 entries and at a clean stop, and a starting node acts on the committed assignments only once its copy is current. In the acceptance suite's node logs, restarted nodes of the build before the readiness condition was complete declined 3 stale epoch-1 assignments met during the replay; the release build declined none. Its 3 remaining declines were at current epochs, where another replica held more of the log, which is what the guard is for. The suite kills its nodes, and none reached 128 entries, so it did not start a node from a snapshot; unit tests cover that.

    Tests thought flaky. TestIsolation_AcknowledgementsBelongToTheirRecipient failed twice in CI (2026-10-13 and 2026-10-21), both before the per-IP rate limiter's out-of-order timestamp stall was fixed on 2026-10-21; it then passed 600 local runs, 300 of them under -race with GOMAXPROCS 1 and 2, and every CI run since. TestClusterRestoredFromBackups, whose log comparison race was fixed on 2026-10-27, passed 5 of 5 runs. Neither needed a change.

    What was run. The unit suites, and the acceptance suite on processes on one Windows machine, passed with the changes; the container tests, the soak and the upgrade drill were skipped there, the container tests running in CI. The release's own checks are recorded on its release page. The environment gates below are unchanged by this release.

    The release. Released from 193d788. Checks on the release itself: pull-request and main CI; the release workflow's image scan (no fixable HIGH or CRITICAL findings) and its network-partition and memory-limited restart tests on the exact image; a local smoke test of that image under a 512 MiB limit; and TestRollingUpgradeAndRollback with the checksum-verified Windows binaries of v0.12.2 and v0.13.0, which passed in 131.69 s with 679, 621 and 718 acknowledged events in its three phases, all delivered, none early, and replica logs in agreement after each phase. 2, 2 and 1 events were delivered more than once.

    v0.12.2 — 2026-11-12¶

    The v0.12.1 upgrade drill left two observations open. Both were examined with the drill rerun under a trace of every redelivered event.

    Redeliveries. The last phase redelivered 74 to 137 events across four runs, the first two phases at most 10. Each burst was one leader, restarted and back before the others saw it go, delivering again every event its consumer group had completed on that partition in the phase. The cause was a defect in how a restarted node reads a group's progress, present since v0.9.0 and fixed in v0.12.2: the floor raised when a partition starts was taken as the group's highest completed offset before the completions recorded above it had been read. The last phase was the one hit because its group's floor could not pass the previous phase's entries of another topic, so all its progress was in those records. With the fix the last phase redelivered 3 and 5 events in two runs. Nothing was lost in any run.

    A second cause. The drill of the first v0.12.2 build, run with its release binaries before publication, still redelivered 38 events in its last phase. Further runs, traced per event and then with the dispatcher's decisions logged, found bursts of 5 to 13 redeliveries a few milliseconds apart at a leader, of events acknowledged up to seconds before, in 6 of 10 traced runs and in every phase. Each burst was a redelivery scan that came in while an acknowledgement raised its group's floor: the new floor was stored, and the records below it removed, before the floor was raised in memory, and the scan found neither. Raising the log start on compaction had the same order, which is why groups waiting behind another topic's entries were hit hardest. The fix, also in v0.12.2, removes the records only after the floor is raised in memory. In six runs with both fixes every redelivery was of an event delivered just before its node was killed, at most 4 in a phase. The first build was not published; its tag and draft release were replaced.

    The take-up guard on ordinary restarts. The committed assignment did not lag. A node that starts replays the cluster's metadata log from the beginning, having no snapshot of it yet, and its leadership loop ran during that replay and saw the first assignments, which named it leader at epoch 1. v0.12.1's guard declined them. v0.12.0 has no guard, but for a restarted process with its disk two older checks hold: a partition refuses an epoch below the one it has durably accepted (its logs show epoch regression: 1 < 3 on such restarts), and a follower refuses log entries and consumer progress from a leader whose epoch is below its own. A node can take back the exact epoch it held, when it is still the committed leader; with its log intact that is correct. After a power loss with batch or periodic fsync its log could end before its followers' at that epoch; v0.12.1 declines that, and v0.12.0 has not been tested in it.

    The release. Released from 0632aa8. Checks on the release itself: pull-request and main CI; the release workflow's image scan (no fixable HIGH or CRITICAL findings) and its network-partition and memory-limited restart tests on the exact image; a local smoke test of that image under a 512 MiB limit; and TestRollingUpgradeAndRollback with the checksum-verified Windows binaries of v0.12.1 and v0.12.2, which passed in 131.39 s with 631, 662 and 622 acknowledged events in its three phases, all delivered, none early, and replica logs in agreement after each phase. 1, 32 and 1 events were delivered more than once; the rollback phase runs v0.12.1 nodes, which still have both defects. The environment gates below are unchanged by this release.

    Dedicated production candidate — closure criteria, 2026-11-05¶

    The first production deployment is dedicated to one application/operator. Schemas are managed as configuration. Shared-tenant storage/in-flight quotas, live schema registration and forced manual rebalance are excluded from this release scope; membership-driven reconciliation remains supported. This scope decision does not claim those excluded features were implemented.

    Schema files must be distributed identically to every node before startup. Malformed/unreadable files, unknown types and duplicate versions now stop startup instead of silently removing validation. A topic with no schema still accepts arbitrary payloads. Deployment preflight must compare the expected topic/version inventory on every node using schema-list/schema-get, and verify a known-invalid payload is refused. Use only the documented schema keyword subset.

    Product fixes in this candidate (not yet released):

    • Publish response failures include error_code. Updated SDKs report internal failures as ErrorKindInternal, exhausted leadership refusals as ErrorKindLeaderChange, and authentication/permission failures as ErrorKindAuth. Old servers retain the legacy response fallback; an internal error can occur after append, so retries must preserve message ID and payload.
    • A valid non-admin dashboard token receives HTTP 403 and "Admin access required"; missing/invalid credentials still receive HTTP 401.
    • Schema loading fails closed and a failed reload preserves the active registry.

    Reference test profile¶

    These are acceptance targets to establish, not measured capacity or a hardware purchase recommendation. Use disposable staging instances on three separate Linux amd64 hosts/failure domains, initially 4 vCPUs, 8 GiB RAM and 100 GiB persistent SSD per node. Record actual disk model/storage service, filesystem and cache semantics. Use replication factor 3, minimum in-sync replicas 2, TLS, JWT/RBAC, encryption at rest and every_event fsync. Pin the exact commit and image digest throughout.

    • Run for 24 hours at 100 events/s; once per hour burst to 500 events/s for 60 s. Use 1 KiB payloads normally and 64 KiB for 1% of events, unique message IDs, dedup enabled, and a mix of immediate and delayed schedules. Seed 100,000 delayed events before injecting failures. Increase this envelope only after it passes and disk/memory headroom is measured.
    • Require zero lost acknowledged events and zero early deliveries. Track every acknowledged ID through delivery and, when enabled, CDC export. Record duplicates separately under the at-least-once contract.
    • Under healthy steady load, target publish p99 <= 250 ms and scheduling lateness p99 <= 1 s; no unexpected refusals. Report the same metrics separately for bursts and disruptions instead of hiding them in whole-run averages.
    • After losing one host, target resumed publish/delivery service within 60 s. After a full backup restore, target service recovery within 30 minutes and zero loss of events acknowledged before the backup's recorded cut. Measure actual backup age separately; later acknowledgements are outside that cut.
    • Include slow consumers, a failed CDC destination, disk pressure, 3-to-5 node growth, drain/replacement and leader loss during catch-up. Do not proceed to another disruption until the ledger and replica state reconcile. Record memory, disk, pinned retention and DLQ journal growth; unexplained unbounded growth or inability to recover within the envelope fails the gate.
    • Test the intended upgrade from v0.11.0 on copied data. Verify the documented on-disk format boundary before rollback; never assume a downgrade is safe. Test controlled host/power loss only on disposable infrastructure using the intended storage. A process kill or VM reboot is not a physical power-cut test.

    Configured tenant rates¶

    Create a persistent JSON file, for example:

    {"publisher-a":{"max_events_per_second":1000},"publisher-b":{"max_events_per_second":100}}

    Start the authenticated server with --tenant-limits-file=/etc/cronos/tenant-limits.json or CRONOS_TENANT_LIMITS_FILE. Subjects are verified JWT subjects, not client-supplied event metadata. Limits apply per node across the subject's topics, with a one-second burst. A batch must fit that burst. Unlisted subjects are unlimited. Restart to load changes; bucket state resets on restart. These are not cluster-wide rate limits.

    With Helm, put that JSON into the existing auth Secret and set auth.tenantLimitsKey to its key name. Restart the pods after updating the Secret. Invalid files and unsupported quota fields fail startup. Storage and in-flight quotas remain unsupported: their counters do not yet have durable recovery or cluster-wide accounting. Do not advertise quota-isolated shared tenancy.

    CDC recovery contract change¶

    Missing, malformed, null, negative-invalid or beyond-log CDC positions now start from the retained log's beginning. First enabling CDC on existing data also exports retained history. Destinations must tolerate duplicates. This cannot restore records already removed by retention; restore them from an appropriate backup if needed. All nodes must use consistent CDC configuration.

    Executable topology coverage¶

    The manual five-node-production-topology workflow uses five kind workers and five Cronos pods with hard anti-affinity. It exercises startup, rolling restart and loss of the first pod's data volume using the production security settings. The ordinary CI smoke profile remains three pods. Both use reduced resource/partition settings for CI. Kind workers share one physical host: this is scheduling/topology coverage, not physical multi-host fault or capacity evidence.

    Gates requiring the target environment¶

    Record the commit and immutable image digest, machine/storage topology, workload, configuration, timestamps and raw logs for each run. Agree on throughput, p99 scheduling lateness, recovery time and acceptable duplicate delivery before testing.

    1. Run a 24–72 hour representative soak on separate hosts, with actual payload sizes and scheduled backlog, slow consumers, a failed CDC sink and disk pressure. Account for every accepted event through eventual delivery/export; measure memory, disk growth, lateness and refusal rates against the agreed limits.
    2. Grow from three to five nodes, replace nodes, drain one at a time, and fail a leader during handoff/catch-up. Verify acknowledged-event conservation and replica agreement before proceeding to the next disruption.
    3. Restore backups containing scheduled events, pending CDC, consumer progress and DLQ records. Measure recovery time and recovery point. Test the intended upgrade path and only supported rollback boundaries on copies of real-sized data.
    4. Perform controlled host/power-loss tests on disposable infrastructure using the intended disks and durability settings. Process kills and kind restarts do not prove that storage honors power-loss durability.
    5. Run candidate CI, race and acceptance suites and fresh Go/Rust/image scans. Preserve failures and diagnose intermittent results. Publish the tested digest.

    Automatic snapshot selection for large replication lag and DLQ journal compaction remain separate engineering work. Bound supported refill/backlog sizes and alert on pinned retention/disk pressure until those paths have measured operating limits.

    Dashboard and feature journey, 2026-11-05¶

    Run against a Windows amd64 build of the working tree. A single authenticated node (real JWTs, RBAC policy, per-subject limits file, persisted schema) and a three-node TLS cluster (the acceptance harness, with a workload) were driven through the dashboard in a browser and through the public RPCs.

    Verified end to end: sign-in with an admin, a non-admin and an expired token (admin APIs refuse the last two); publish, deduplication, schema rejection, delivery no earlier than the scheduled time, acknowledgement and replay; cluster topology with leaders, replicas and in-sync sets; partition health; replication lag; consumer groups and committed-offset lag; schemas; tenant usage with configured limits; retention and compaction actions; manual rebalance reported as unsupported.

    Defects found and fixed:

    • JSON schema validation ignored required, so {} was accepted by a schema that requires order_id. It is now enforced; other keywords (enum, pattern, ranges, additionalProperties) are still not enforced.
    • The dashboard's replication view could not show partition 0 (the HTTP API treated partition_id=0 as "all partitions") and titled partition 0 "All Partitions". The HTTP API now treats an explicit 0 as partition 0; the RPC keeps 0 as "all".
    • The dashboard labelled the per-node leader count "Leader Partitions" beside the cluster-wide total, so a node leading nothing showed 0 while every partition had a leader. It is now "Led by this node".
    • AckRequest.next_offset was documented as optional, but a successful ack with any value other than the highest delivered offset plus one is rejected. The comment now says so; the client library already sends it.

    Limits left as they are: replication lag is only reported by a partition's leader (the cluster view has the same information from any node), while partition health is local to each node and answers for any partition the node holds; retention and compaction take 0 as "all local partitions", so partition 0 cannot be targeted alone; a node serves the dashboard assets compiled into it, and the files checked in under internal/api/web/dist are older than the source (the Docker build stages a fresh build, a plain go build does not).

    Acceptance campaign on this host: every test passed except TestOverloadIsRefusedAndSurvived, which failed in 1 of 4 runs of this tree and in 3 of 7 runs of an unmodified HEAD worktree, and in 2 of 2 runs of the cgo build in a Linux container. In failing runs the nodes took the whole 624 MiB flood without refusing. The evidence points at the test, not the nodes: its events fell due 45 seconds into the flood, and the failing runs were the slow ones (about 90 events/s instead of 200), which outlast that window; the mechanism, that an event which is due no longer counts toward the memory the guard measures, is inferred, not observed. With the due time at 20 minutes the nodes refused as designed (one run). The test now schedules its events 150 seconds out. With that change it passed 4 of 4 runs in the Linux container and 4 of 4 on Windows (about 160 s each, up from about 55 s).
